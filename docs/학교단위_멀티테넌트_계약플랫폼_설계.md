# 학교단위 멀티테넌트 계약업무 플랫폼 설계

## 1. 최종 목표

딸깍 계약업무는 장기적으로 다음 3개 계약영역을 모두 지원한다.

- 공사(WORKS)
- 용역(SERVICE)
- 물품(GOODS)

세 영역을 각각 별도 프로그램으로 만들지 않고,
**하나의 계약 사건카드(Contract Case)** 를 공통으로 사용한다.

공통 절차·현황판·나라장터 연동·문서이력은 공유하고,
법령판정과 문서템플릿만 업무영역별 모듈로 분리한다.

---

## 2. 공통 사건카드

모든 계약은 아래 공통정보를 가진다.

- 기관(org_id)
- 회계연도
- 사건 순번
- 계약영역: 공사 / 용역 / 물품
- 세부업무 유형
- 계약명
- 담당자
- 현재 상태
- 현재 해야 할 일
- 기한
- 예산액
- 추정가격
- 기초금액
- 계약금액
- 나라장터 공고번호
- 공고일 / 개찰일 / 계약일
- 적용 Rule 버전
- 생성 문서 이력

예시:

- CHN-○○초-2027-S-001: 통학차량 임차용역
- CHN-○○초-2027-G-002: 복사용지 구매
- CHN-○○초-2027-W-003: 교실 바닥 교체공사

---

## 3. 계약영역별 모듈

### 공통 Core

- 기관/사용자/권한
- 계약 사건카드
- 현황판
- 일정/기한
- 나라장터 사건 연결
- 문서 생성 이력
- HWPX 출력
- 감사/변경 이력
- 알림

### SERVICE

현재 개발 중인 모듈을 그대로 사용한다.

- 소액수의 Rule Engine
- 통학차량
- 여객 육상운송 적격심사
- 수학여행
- 방과후·늘봄
- 시설 유지관리 등

### GOODS

향후 추가:

- 소액수의
- 중소기업자간 경쟁제품
- 직접생산
- 다수공급자계약(MAS) 등 조달 관련 분기
- 일반/제한경쟁
- 물품 적격심사 또는 낙찰기준
- 검수·물품등록 연계

### WORKS

향후 추가:

- 전문/종합공사 구분
- 공사예정금액·추정가격
- 업종·주력분야
- 지역제한
- 적격심사
- 건설산업기본법 관련 자격
- 공사계약 문서
- 착공/준공/검사/하자관리

## 4. 학교가 독립적으로 붙는 구조

학교 한 곳을 하나의 **Organization / Tenant** 로 본다.

Firestore 예시:

organizations/{org_id}
  contracts/{case_id}
  members/{membership_id}
  settings/{setting_id}

사용자는 자신이 ACTIVE 멤버인 조직의 계약만 조회할 수 있다.

### 권장 가입 흐름

1. 사용자가 로그인
2. 학교/기관 검색 또는 기관코드 입력
3. 기존 기관이면 가입요청
4. 기관 관리자가 승인
5. 승인 후 해당 학교 현황판 사용

기관이 아직 없으면:

1. 학교 검색/기관코드 입력
2. 새 기관 작업공간 생성 요청
3. 기관 검증
4. 최초 승인 사용자를 기관관리자로 지정

### 자동 가입을 너무 느슨하게 하지 않는 이유

학교명만 같거나 이메일 도메인만 같다는 이유로 자동 가입시키면
다른 기관의 계약정보에 접근할 위험이 있다.

따라서 '알아서 붙는 느낌'은 유지하되 내부적으로는 다음 중 하나를 사용한다.

- 기관코드 기반 매칭
- 기관 초대코드
- 승인된 기관관리자 승인
- 향후 기관 인증수단 연계

---

## 5. 상위기관 구조

Organization은 parent_org_id를 가질 수 있다.

예:

충청남도교육청
  └ 천안교육지원청
      ├ ○○초등학교
      ├ △△중학교
      └ □□고등학교

그러나 **상위기관이라고 자동으로 하위 학교 계약을 볼 수 있게 하지 않는다.**

지원청/교육청 통합현황이 필요한 경우 별도의 권한을 명시적으로 부여한다.

이 원칙은 학교 단위 데이터 격리와 최소권한을 위한 것이다.

---

## 6. 현황판

학교 로그인 후 첫 화면은 계약 현황판으로 구성한다.

### 상단 요약

- 전체 진행중
- 오늘 할 일
- 확인 필요
- 공고 중
- 적격심사 중
- 계약체결 대기
- 완료

### 계약카드

각 카드:

- 계약명
- 공사/용역/물품 배지
- 현재 단계
- 나라장터 공고번호
- 담당자
- 다음 할 일
- 다음 기한
- 금액
- 경고/확인필요

### 오늘 할 일

- 오늘 개찰
- 공고 종료
- 적격심사 제출기한
- 계약체결 예정
- 검사/검수 예정
- 지연된 업무

## 7. 상태 흐름

공통 상태값을 사용한다.

DRAFT
→ INTERNAL_REVIEW
→ NOTICE_PREPARATION
→ NOTICE_OPEN
→ BID_OPENING
→ QUALIFICATION_REVIEW
→ AWARD_DECISION
→ CONTRACT_PREPARATION
→ CONTRACTED
→ PERFORMANCE
→ INSPECTION
→ PAYMENT
→ COMPLETED

필요 없는 단계는 계약유형별로 건너뛴다.

예:

1인 수의 물품:
DRAFT → INTERNAL_REVIEW → CONTRACT_PREPARATION → CONTRACTED → INSPECTION → PAYMENT → COMPLETED

통학차량 경쟁입찰:
DRAFT → NOTICE_PREPARATION → NOTICE_OPEN → BID_OPENING → QUALIFICATION_REVIEW → AWARD_DECISION → CONTRACTED → PERFORMANCE → COMPLETED

## 9. 나라장터 연동 원칙

나라장터 데이터는 계약 사건카드의 외부 데이터원이다.

- 공고번호 저장
- 공고 정보 동기화
- 개찰 결과 동기화
- 낙찰 결과 동기화
- 계약정보 동기화

나라장터 상태가 변해도 내부업무 상태를 무조건 덮어쓰지 않는다.

예:
- G2B 개찰결과 발생
  → 사건카드에 '개찰결과 확인 필요' 이벤트 생성
  → 담당자가 확인 후 QUALIFICATION_REVIEW 상태로 전환

---

## 10. 바로 적용할 개발원칙

지금부터 새 기능은 모두 다음을 전제로 만든다.

1. org_id 없이 계약을 영구 저장하지 않는다.
2. domain(WORKS/SERVICE/GOODS)을 모든 사건에 둔다.
3. 용역 전용 정보는 ContractCase 공통필드에 억지로 넣지 않고 subtype 모듈 데이터로 분리한다.
4. 법령 Rule Engine은 domain별로 분리한다.
5. HWPX·나라장터·현황판은 공통 Core 기능으로 둔다.
6. Firestore 연결 전에도 저장소 코드의 모델은 멀티테넌트를 전제로 한다.
